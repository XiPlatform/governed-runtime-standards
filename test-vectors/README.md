# Test vectors

Canonical inputs and expected outputs for the [Action Provenance Record](../specs/action-provenance.md) and the [Action Approval Attestation](../specs/action-approval.md), version 1.0. An independent implementation, in any language, can check its canonical serialisation, digests, MACs, chain verification, coverage evaluation and conformance-level reporting against these files.

The vectors are generated by the reference implementation (`npm run test-vectors`, see [`scripts/generate-test-vectors.mjs`](../scripts/generate-test-vectors.mjs)) and checked against it on every change by [`test/test-vectors.test.ts`](../test/test-vectors.test.ts). Every document in them also validates against the JSON Schemas ([`test/schema.test.ts`](../test/schema.test.ts)). Where a vector and the specification text disagree, the specification prevails and the disagreement is an erratum; please report it as an issue.

## Files

| File | Specification sections | What it tests |
|---|---|---|
| [`canonical-form.json`](canonical-form.json) | APR 5 | Canonical serialisation of JSON text: member order by UTF-16 code units, whitespace, literals, number formatting, string escaping, nested arrays. Each vector gives the canonical string, its UTF-8 bytes in hex, and its SHA-256 digest. |
| [`content-digest.json`](content-digest.json) | APR 5, 6.1; AAA 6 | Content digests of the worked examples and of edge cases: the top-level `integrity` member is removed, a nested member of the same name is not. |
| [`seal-and-verify.json`](seal-and-verify.json) | APR 6.2, 6.5; AAA 6 | HMAC-SHA256 seals of records and attestations under a published test key, and verification cases: unchanged, `sealedAt` changed, content changed, wrong key, altered MAC, missing MAC, unsealed. |
| [`chain.json`](chain.json) | APR 6.4 | A three-record chain from genesis, with link messages and proofs, and chain verification cases: intact, segment, gap, reordered, broken `prev`, changed content, forged link, wrong scope. |
| [`coverage.json`](coverage.json) | AAA 4, 5 | Whether a grant covers a proposal: exact match, changed arguments, other correlation, effect mismatch, rejected, revoked, expiry boundary, use-limit boundary, `matchOn` mismatches, session matching, `auto` grants. |
| [`conformance-levels.json`](conformance-levels.json) | APR 7.2; AAA 7.2 | The highest level a record or attestation reaches, from 0 to 3, for the examples and for documents that fail a specific rule. |

## Format

Every file is a JSON object with a common header:

- `title`, `specs`: what the file covers.
- `generator`: the reference implementation version that produced it.
- `notes`: how to read the file, including which expected values are normative and which are informative.

Expected values that the specifications define, such as a canonical string, a digest, a MAC, whether a chain verifies and the first failing sequence number, whether a grant covers a proposal, and a conformance level, are normative. Result codes such as `reason: "args_mismatch"`, the `verified` count of a chain, and the JSON Pointer paths [RFC 6901](https://www.rfc-editor.org/info/rfc6901) in `failingAtNextLevel` are what the reference implementation reports; the specifications do not define them, so other implementations need not match them.

In `canonical-form.json`, `input` is JSON *text*, not a parsed value, so that number spellings such as `1.0`, `-0` and `2E3` and string escapes are preserved exactly. Parse it with a conforming JSON parser before canonicalising.

In `coverage.json`, `check.now` is a timestamp, `check.usesSoFar` is the number of executions already made under the grant (0 when absent), and `rule` is the step of the coverage algorithm in AAA section 5 that decides the case.

## Test keys

`seal-and-verify.json` and `chain.json` publish two HMAC keys, given as text (`secret`) and as the hex of its UTF-8 encoding (`secretUtf8Hex`). They are public test values. **Never use them to seal real records.**

| Key identifier | Use |
|---|---|
| `test-vector-key-1` | Seals every vector. |
| `test-vector-key-2` | Verification with the wrong key, and the forged chain link. |

All seals use a fixed `sealedAt` of `2026-09-02T04:00:00.000Z`. Because `sealedAt` is not covered by any proof, an implementation that sets a different time produces the same digests and MACs.

## Using the vectors

A minimal check of another implementation, in outline:

```text
for v in canonical-form.vectors:
    c = canonicalise(parse_json(v.input))
    assert c == v.canonical and sha256_digest(c) == v.sha256

for v in content-digest.vectors:
    assert content_digest(v.document) == v.contentDigest

for v in seal-and-verify.vectors:
    assert hmac_sha256_base64url(utf8(key.secret), utf8(v.contentDigest)) == v.mac.value

for c in chain.chainCases:
    (ok, firstFailingSeq) = verify_chain(c.records, key, c.scope)
    assert ok == c.expected.ok and firstFailingSeq == c.expected.brokenAtSeq

for c in coverage.cases:
    assert covers(coverage.grants[c.grant], c.check) == c.expected.covered

for c in conformance-levels.cases:
    assert level(c.document) == c.expectedLevel
```

[`test/test-vectors.test.ts`](../test/test-vectors.test.ts) is a complete TypeScript version of these checks.

## Regenerating

After a change to the reference implementation that is meant to change an output, regenerate the vectors and review the difference:

```bash
npm run test-vectors
git diff test-vectors/
```

A change to an expected normative value is a change to the specification's behaviour. It needs an erratum or a new version, as described in [GOVERNANCE.md](../GOVERNANCE.md), and cannot be made as a routine code change.
